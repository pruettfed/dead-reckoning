# Dark Vessel Detection

Maritime OSINT platform: detect ships in Sentinel-1 SAR (radar) imagery, cross-reference live AIS, flag "dark vessels" (visible in radar, not broadcasting AIS). Each SAR pass is an independent snapshot correlated against AIS at its acquisition time.

- **Deeper docs:** `docs/architecture.md` (pipeline detail + file map — read before touching `backend/app/`), `README.md`, `docs/api.md`, `docs/ais-coverage.md`.

## Pipeline

1. **AIS ingest** (`ais.py`, `ingest.py`) — AISStream WebSocket → PostGIS, continuous; switching the frontend ROI is a view filter only, never narrows ingestion.
2. **SAR detect** (`sar.py`, `detect.py`) — newest Sentinel-1 IW GRDH pass fetched as VV chips (Process API, tiled), run through tiled YOLOv8 → centroids + confidence (high/med/low).
3. **Land mask** (`landmask.py`) — detections inside `land_polygons` flagged `on_land`, excluded from fusion and counts. Load with `scripts/load_land.py` (0 PU).
4. **Fusion** (`fusion.py`) — AIS dead-reckoned to the acquisition instant (`sog`/`cog`), matched one-to-one against a physical uncertainty budget (`MATCH_RADIUS_M` + SAR azimuth displacement + fix-age drift), clipped to `sar_bbox` ∩ image-footprint. Three states: `matched` / `dark` / `indeterminate`. Every scene measures its own false-match rate on empty water and withholds dark calls above `MAX_CHANCE_MATCH_RATE`. Skipped entirely for `survey` ROIs (`is_dark` stays NULL).
5. **Schedule** (`scheduler.py`) — a lifespan task sweeps all 12 ROIs every `SCHEDULER_INTERVAL_SECONDS` and analyzes each new usable pass once, under a `PU_MONTHLY_CEILING`. Nobody requests imagery; the admin POST survives as an ops escape hatch outside production only, alongside `scripts/analyze.py`.
6. **Surface** (frontend) — react-leaflet; selecting a scene freezes the vessel layer at its time (scene = time control); the client is read-only and holds no key. The map draws both ROI boxes and drapes the stored SAR overview under the detections; the sidebar shows a next-pass countdown and the cross-region schedule. The UI is the Console v4 layout: three columns (region rail / map / contact rail), state-grouped contacts, and a per-contact dossier with fusion evidence and cross-scene sighting history.

## Constraints (correctness / budget guardrails)

- **PostGIS everywhere** — never SQLite in Docker or prod.
- **Fusion in SQL** — PostGIS owns every metre (dead reckoning via `ST_Project`, matching via `ST_DWithin`); never reimplement distance in Python. Only the one-to-one assignment is Python, because it is combinatorics, not geometry.
- **Never match raw AIS positions** — median cadence is 168 s, 864 m of travel at 10 kn, further than any sane radius. Dead-reckon to the acquisition instant or the match is meaningless. Match gates must include the SAR azimuth displacement of a moving target (~450 m at 10 kn) or ordinary traffic reads as dark.
- **A dark count is not a result without its noise floor.** Every fused scene probes empty water and stores `chance_match_rate`; above `MAX_CHANCE_MATCH_RATE` darks are withheld as `indeterminate`. Re-measure with `scripts/refuse.py` (0 PU) — never tune the gate by intuition. Full derivation: `docs/fusion-rework.md`.
- **An empty AIS buffer measures as a *confident* all-dark scene, not as a failure** — which is why `coverage_ok` brackets the scene on **both** sides (`[T−window, T+window]`), not just the floor. A floor-only check passed a fresh scene whenever ingest had died but its rows were still inside the retention window: fusion then matched nothing, `measure_chance_match` returned 0.0 (no false matches are possible against an empty set), `discriminating` came out **True**, and every detection was classified `dark`. The output looks statistically sound and is entirely wrong, and it costs PU to produce. Three layers now stop it, deliberately redundant: the scheduler gate (routine path), an explicit staleness refusal in `find_target_scene` (covers `scripts/analyze.py` and the admin POST, which bypass the scheduler), and `coverage_ok` itself (covers `scripts/refuse.py`, which re-fuses stored scenes at 0 PU and reaches neither of the other two). The ceiling costs nothing real: it makes the effective minimum scene age 2h behind the newest AIS, and `MIN_SCENE_AGE` is already 3h.
- **Recall is reported against resolvable hulls only** (AIS ship_type 60–89) — at 10 m/px a fishing boat is under the sensor, so counting it measures Sentinel-1, not the model. Trusted from either AIS class (A or B): `ship_type` is a self-declared hull category, not a function of transponder class, and there is no independent size check (e.g. AIS `Dimension`) to cross-verify it either way — a mis-declared Class B unit would inflate the denominator undetected.
- **Clip to ROI ∩ footprint** — a detection outside the imaged footprint is unobserved, not dark. Never mosaic passes for correlation (different times = vessels moved).
- **PU budget 30,000/mo** — only pixel fetch spends PU (~18–107/analysis, scales with `sar_bbox` area — see `estimate_pu`); catalog search free. Scenes DB-cached (re-analysis = 0 PU). Never discover via Copernicus Browser (burns PU). Cost is *usable passes × PU/pass* — price with `backend/scripts/probe_regions.py` (free), never by intuition. `test_monthly_pu_within_budget` fails the build if the registry exceeds budget.
- **A pass must actually image the box** — the catalog's "intersects" is not enough: a swath clipping one corner costs full PU and returns a black chip. `find_target_scene` computes the mosaicked footprint's coverage of `sar_bbox` in PostGIS and refuses below `MIN_FOOTPRINT_COVERAGE` (85%), before any spend. Coverage is the union over the Process API's `[-1 min, +10 min]` window (`PROCESS_WINDOW_BACK`/`FWD`), not one slice — keep those constants in sync with `build_process_request`. Roughly half of all passes fail this; `passes_per_month` in `rois.py` counts only the ones that pass. That pre-fetch check trusts the catalog's *reported* footprint polygon, which can be wrong — found on `gulf_of_finland` 2026-08-03, catalog said ~99%, the Process API actually returned ~50% (black, not water). The evalscript's `dataMask` band (`SarChip.mask`) gives a ground-truth recheck after the fetch: `_run_analysis` re-measures real coverage against the same `MIN_FOOTPRINT_COVERAGE` and raises `SarCoverageTooLow` below it, same failure path as any other pipeline error (PU already spent either way; `scene_has_pu_spend` stops a retry).
- **A deleted scene row is not a new scene, for PU purposes** — `scripts/dev_reset.py` deletes `sar_scenes` rows to force a re-fetch (intended, documented there), but `pu_ledger` is deliberately never touched by that reset. `scheduler.decide()` used to only check `has_pu_spend` when `status == "failed"`; a deleted row reads as `status=None`, indistinguishable from a genuinely new pass, and that branch fell through to an unconditional "new pass" — silently re-spending PU on a scene already paid for, once per accidental re-reset (found 2026-08-04: the same `gulf_of_finland`/`north_taiwan` scenes re-fetched 3x each, ~2,000 PU of duplicate spend). Fixed by checking `has_pu_spend` unconditionally, before the status branches — a scene ID with any `pu_ledger` entry is skipped regardless of whether its row exists.
- **A fresh catalog listing is not fresh pixels** — CDSE can list a product before the Process API actually has its pixels ready; the pre-fetch footprint check has no way to see that, since it only has the catalog's polygon. `find_target_scene` skips any candidate under `MIN_SCENE_AGE` (3h, a conservative starting point off two data points, not a measured threshold) before considering it, falling back to an older candidate in the same window if one exists. `estimate_next_pass` adds the same offset to what it reports, so the UI's countdown reflects when analysis will actually start, not just when the satellite flies over — without it, "next acquisition" reads as overdue for hours before anything happens.
- **Analysis is scheduled, never requested** — `scheduler.py` is the only routine path to a pixel fetch. **Production exposes no PU-spending endpoint at all**: `POST /api/analysis/{roi}` is registered only outside production (`register_ops` in `main.py`) and 404s there even with a valid `X-Analysis-Key`. It bypasses `PU_MONTHLY_CEILING`, and a scene that fails *after* its fetch is re-bought on every call — the scheduler is protected from that by `scene_has_pu_spend`, that path never was. Forcing a run in prod is `scripts/analyze.py` over a shell. The frontend has no trigger and no key. All availability checks run before any PU is spent.
- **A fetch that already cost PU is never auto-retried.** `pu_ledger` records every spend *before* the request (a fetch that dies mid-flight still cost money). A `failed` scene with a ledger entry is skipped permanently — retrying it each sweep would drain the month. A `failed` scene *without* one is free to retry. `PU_MONTHLY_CEILING` (default 24,000) caps scheduled spend under the 30,000 budget; it deliberately does **not** gate the ops endpoint. Verify guard changes by booting with `PU_MONTHLY_CEILING=0` and reading the per-region skip reasons at `LOG_LEVEL=DEBUG` — a full decision matrix at zero spend.
- **Two ROI boxes, opposite shapes** (`rois.py`) — `ais_bbox` is free, so it stays wide and hugs the coast (terrestrial receivers do); `sar_bbox` costs PU, so it stays small and on water. `sar_bbox` ⊂ `ais_bbox` *strictly* (nonzero margin on every side, not just contained — enforced in `test_rois.py`), both ≤ ~250 km (one IW swath). Never water-center an `ais_bbox` — it collapses coverage. **Placing a `sar_bbox` inside a real swath track matters more than making it small** — repositioning `north_taiwan` took it from 3/11 usable passes at 179 PU to 11/11 at 65 PU. Open ocean gets no IW coverage at all; open-water corridors get grazed, never imaged. Always re-probe after moving one. **AIS coverage inside a `sar_bbox` must also be spatially uniform**, not just present somewhere in the box — a receiver-range cliff hiding inside an otherwise-"covered" box silently forces every detection past it to read "dark" (found in `bosphorus_marmara` 2026-07-26; see `docs/ais-coverage.md`).
- **Land is masked geometrically, never learned** — a rock is not a vessel, and the fact that separates them is geographic. `landmask.py` flags detections inside `land_polygons`; fusion and counts skip them. Detections are *flagged, not deleted*: re-detecting needs a pixel re-fetch (the full-res chip is never persisted, only the overview), but re-masking is a free SQL recompute, so `LAND_MASK_BUFFER_M` retunes at 0 PU via `scripts/load_land.py`. Buffer defaults to 0 — widening it masks berthed and anchored vessels, which is a real loss in the port ROIs. Coastline data itself loads automatically on every boot from a committed export (`app/land/land_polygons.geojson`, a few MB, clipped to the 12 `sar_bbox`es) — `landmask.load_bundled_polygons` is a no-op once `land_polygons` is non-empty, same pattern as the schema auto-migration. That export is generated by `scripts/load_land.py --download` (fetches the ~900 MB OSM WGS84 shapefile itself, no manual download) and must be regenerated and re-committed whenever an ROI's `sar_bbox` moves. The deployed image never carries the raw OSM shapefile, only that small clipped export.
- **Survey ROIs never say "dark"** — regions with no AIS coverage run with `mode="survey"`: fusion is skipped, `is_dark` stays NULL, and the UI shows amber "observed vessel" plus a no-ground-truth banner. Red is reserved for a claim we can actually support.
- **Config from env** — CORS, CDSE creds; never hardcoded. `.env` never committed; `.env.example` is the contract. `DATABASE_URL` is normalized to `postgresql+asyncpg://` in `config.py`, so a platform's plain `postgresql://` can be referenced verbatim. No imagery in repo (`.gitignore` excludes `*.tif`/`*.geotiff`/`*.nc`/`data/`); `*.pt` is excluded too **except `backend/models/*.pt`**, which ships in the image because the scheduler is inert without it.
- **`ENV` gates the destructive surface, and defaults to `production`** — a forgotten value fails closed. Prod serves no `/docs`/`/openapi.json`, allows only `GET`/`OPTIONS` CORS, and **never registers** the `/api/dev/*` reset router (404 even with a valid key; absent from the schema). `ENV=production` with `DEVTOOLS_ENABLED=true`, a wildcard `CORS_ORIGINS`, or a sub-32-char `ANALYSIS_API_KEY` refuses to boot. Dev resets (scenes / AIS / `pu_ledger`) live in `devtools.py` behind `DEVTOOLS_API_KEY`, or keyless via `scripts/dev_reset.py`. **Resets re-spend PU by design** — a deleted scene reads as a new pass to `scheduler.decide`, so the next sweep re-fetches it; set `SCHEDULER_ENABLED=false` first. Secrets are redacted out of `last_error` before the unauthenticated `/api/health` serves it.
- **Compose mirrors prod** — deploy is a config swap, not a rewrite; `--reload` is dev-only.
- **Torch never lives in the API process** — detection runs in a `spawn`ed subprocess that exits (`detect_worker.py`). The scheduler used to `load_detector` at boot and hold ~1 GB resident for the whole month to serve ~152 analyses, a 1.7% duty cycle; on usage-metered hosting that one line was most of the bill (~$17/mo vs ~$8.50). Lazy loading does **not** substitute — at five analyses a day the model is resident within hours — and neither does dropping the reference, because modules never unload from `sys.modules`. Only a process that exits returns the memory. `app/detect.py` stays importable without torch (`from ultralytics import YOLO` is inside `YoloDetector.__init__`); keep it that way. `run_detection` in-process survives for the CLI tools, where a resident model is correct.
- **The scheduler's AIS gate is re-evaluated every sweep, and splits by ROI mode** (`warmup_gate`). It is not a one-shot warm-up: an outage that starts mid-flight re-holds the fused regions on the next sweep, and recovery starts a *fresh* warm-up rather than resuming the old one.
  - **Fused ROIs are gated on AIS continuity with no cap** — held indefinitely while AIS is unhealthy. Costs nothing: without AIS they already refused in `find_target_scene`. What it buys is the stale case, which used to slip through — see the two-sided `coverage_ok` note below.
  - **Survey ROIs keep `SCHEDULER_WARMUP_MAX_HOURS` (8)**, released regardless. They skip fusion, so they are correct with no AIS at all; the cap is what still runs them on a deployment with no `AISSTREAM_API_KEY`. This is the load-bearing half of the old design and it is deliberately unchanged (`warmup_gate` *calls* `warmup_ready` rather than reimplementing it, so the two cannot drift).
  - **Continuity, not depth.** `SCHEDULER_WARMUP_HOURS` (6) of AIS is required with no gap wider than `SCHEDULER_AIS_GAP_MINUTES` (30). Depth from `min(ais_positions.time)` was blind to gaps: after a 12h outage, rows from before it survive the retention prune (`AIS_RETENTION_DAYS`), so depth still read days one minute after recovery — and the longer the retention, the longer that lie holds. Probed by bucketing the window and asking whether each bucket holds a row — **anchored on `now()` counting backwards, never `date_trunc`**. A forward `generate_series(start, now(), step)` emits a trailing bucket running into the future that reads empty seconds after every rollover, which would re-hold every fused region for a full warm-up at each boundary, forever (measured: 5 false gaps in 60 sampled offsets; the shipped form, 0).
  - Served by `ix_ais_positions_time` (added in `ingest.apply_schema`; `create_all` never adds an index to an existing table). Verified as 12 index-only probes, no seq scan, 0.2 ms on 619k rows. Diagnose with `scripts/ais_health.py` (0 PU) — it runs the same query and the same predicates the gate does.
  - Compose sets `SCHEDULER_WARMUP_HOURS: 0` for dev, which disables the gate outright. It sets *only* that, leaving the cap at 8 — and `warmup_ready` used to skip its depth branch on an empty database and then block on that cap, so local dev sat idle for eight hours. Both predicates now short-circuit on `required_hours <= 0`.
- **The API publishes only what a response model declares** — every endpoint has one (`schemas.py`). Responses were hand-built dicts from explicit SELECT lists, which is safe exactly until someone adds a column: that is how `sar_scenes.error` came to serve 500 characters of raw exception text (CDSE URLs, SQL statements, the DSN) on an unauthenticated endpoint. Failures are classified server-side into a **closed** set (`failures.py`) — an unrecognised error reads as the generic phrase rather than falling back to the exception string, which is the fallback that would leak it back. Error text is redacted by `sources.redact` *before it is stored*, not just before it is served.
- **A public SPA cannot hold a secret** — so there is deliberately no API token; one baked into the bundle would be decoration. What protects the surface instead: single origin (the API has no hostname of its own), rate limiting, security headers with a CSP, response models, and production registering no PU-spending or destructive route at all. If asked to "lock down the API", say this rather than shipping a token.
- **The status banner is another shell-only ops surface** — `scripts/status_message.py` (`post`/`toggle`/`clear`/`show`) writes the singleton `status_message` row directly over the database, with no HTTP write path in any environment; `GET /api/status-message` is the sole (public, unauthenticated, free) way to read it back.
- **Middleware order is load-bearing** — Starlette makes the *last* registered middleware outermost. Security headers must wrap the rate limiter, or a 429 goes out bare. Covered by `tests/test_middleware.py`.
